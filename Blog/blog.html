building a kubernetes rag chatbot with langgraph and portkey

July 2026 • 6 min read

what we’re building

A Kubernetes assistant powered by Retrieval-Augmented Generation. You ask questions about pods, deployments, autoscaling, or any K8s topic in plain English — the system retrieves relevant documentation from a vector database, reranks the results, and generates a grounded answer using a large language model. Every step is transparent: you see the thinking trace, the source chunks, and the confidence scores.

The stack is designed for production from day one. A LangGraph agent orchestrates a six-node pipeline. Groq (openai/gpt-oss-20b) powers both the main generator and the guardrail calls, with Portkey as the fallback gateway. Gemini gemini-embedding-001 produces 3072-dimensional embeddings stored in Qdrant Cloud with COSINE distance. FlashRank cross-encoders rerank the top 10 results down to the 5 most relevant chunks.

The frontend is a Next.js App Router application with a sidebar for conversation management, expandable thinking traces, and source citation cards. The backend is FastAPI with asyncpg connecting to NeonDB for persistence and Upstash Redis for response caching.

the architecture

The full architecture is documented in the diagram below. Each component runs as a managed service or is containerized for deployment.

agent pipeline

The LangGraph agent executes six nodes in sequence:

1. input guard — classifies whether the query is Kubernetes-related using a dedicated LLM call. Non-K8s queries are rejected early.
2. router — identifies the intent category (architecture, autoscaling, job management, monitoring, cronjobs, general K8s) to optionally narrow the search scope.
3. retrieve — embeds the query with Gemini and searches Qdrant for the 10 most similar document chunks.
4. rerank — applies a FlashRank cross-encoder to rescore and select the top 5 chunks, improving precision over raw vector similarity.
5. generate — builds a prompt with the reranked context and calls the LLM via Groq to produce the final answer.
6. output guard — verifies that the answer is grounded in the retrieved sources, returning a groundedness fraction.

Thinking steps from each node are captured separately from the conversation messages and rendered as an expandable section in the UI. This keeps the chat clean while allowing full transparency into the agent’s reasoning.

key stack decisions

Groq direct with Portkey fallback. All LLM traffic runs through Groq’s openai/gpt-oss-20b for low-latency inference. A separate Groq client handles guardrail calls so they never compete with the main generator for tokens. Portkey remains the gateway fallback when no Groq key is configured.

Gemini embeddings. We use Google’s gemini-embedding-001 model which produces 3072-dimensional vectors with a free-tier rate limit of 100 req/min. Batching is set to 10 with exponential backoff retry (30s initial, +5s per attempt, max 5).

Qdrant Cloud. Chosen for its managed vector database with COSINE distance support and a straightforward gRPC/REST API. Collection is configured with 3072 dimensions. Upserts use 120s timeout and 50-point batches.

FlashRank over Cohere/LLM reranking. The ms-marco-TinyBERT-L-2-v2 cross-encoder runs locally with no API costs or latency. It reranks 10 chunks to 5 in well under 100ms on CPU.

NeonDB (serverless PostgreSQL). We use asyncpg for connection pooling and SQLAlchemy async for ORM. Neon’s URL includes sslmode and channel_binding parameters which are stripped for asyncpg compatibility.

Upstash Redis for caching. Response caching uses SHA256 query hashes with 24-hour TTL. On cache hit, the entire agent pipeline is skipped — zero LLM calls. The REST API is accessed via HTTPS (port 443) to avoid firewall issues with the Redis protocol port (6379).

how the pieces connect

Beyond the diagram, it helps to see the actual code that wires this together. The whole pipeline is a single FastAPI process with lazy-initialized singletons for every external dependency — Qdrant, Gemini embeddings, the Groq-backed LLM, and the FlashRank reranker. They are bootstrapped once at startup inside the app’s lifespan and closed cleanly on shutdown: 

@asynccontextmanager
async def lifespan(app: FastAPI):
    if settings.langsmith_api_key:
        os.environ["LANGSMITH_TRACING"] = "true"

    await db_manager.initialize()
    await redis_manager.initialize()
    await qdrant_manager.initialize()
    await embedding_manager.initialize()
    await llm_manager.initialize()
    await reranker.initialize()
    yield
    await db_manager.close()
    await redis_manager.close()
    await qdrant_manager.close()
    await embedding_manager.close()
    await llm_manager.close()
    await reranker.close()

Importing the heavy SDKs (portkey, qdrant-client, google-genai, flashrank, langgraph) at module load made cold starts take minutes. Each manager now imports its SDK lazily inside initialize(), cutting startup from ~200s to under 4 seconds.

the agent graph

LangGraph is the conductor. Six nodes run in sequence, with a single conditional branch: the input guard decides whether a query is even about Kubernetes. If not, we short-circuit to a reject node instead of burning LLM and vector-store calls. 

def build_graph():
    from langgraph.graph import StateGraph, END

    builder = StateGraph(AgentState)

    builder.add_node("input_guard", input_guard_node)
    builder.add_node("reject", reject_node)
    builder.add_node("router", router_node)
    builder.add_node("retrieve", retrieve_node)
    builder.add_node("rerank", rerank_node)
    builder.add_node("generate", generate_node)
    builder.add_node("output_guard", output_guard_node)

    builder.set_entry_point("input_guard")
    builder.add_conditional_edges(
        "input_guard", route_after_guard,
        {"router": "router", "reject": "reject"}
    )
    builder.add_edge("reject", END)
    builder.add_edge("router", "retrieve")
    builder.add_edge("retrieve", "rerank")
    builder.add_edge("rerank", "generate")
    builder.add_edge("generate", "output_guard")
    builder.add_edge("output_guard", END)

    return builder.compile()

State flows through the graph as a typed dict. Chunks and thinking steps accumulate with an operator.add reducer, so each node’s output is merged into a shared state that the next node reads. 

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]
    user_query: str
    intent: str
    retrieved_chunks: list
    reranked_chunks: list
    generated_answer: str
    sources: list
    thinking_steps: Annotated[list, operator.add]

    guardrail_output_passed: bool
    conversation_history: str

guardrails

The input guard is a small dedicated LLM call that answers only PASS or REJECT. It runs against a separate Groq client (openai/gpt-oss-20b) so guardrail traffic never competes with the main generation model for tokens. 

async def input_guard_node(state: dict) -> dict:
    query = state["user_query"]
    system = (
        "You are a safety and Kubernetes topic classifier. "
        "Reply ONLY with PASS or REJECT."
    )
    result = await llm_manager.generate_guard(system, query, max_tokens=100)
    passed = "pass" in result.strip().lower()
    return {"guardrail_input_passed": passed, "thinking_steps": [step]}

retrieve + rerank

Retrieval embeds the query with Gemini and searches Qdrant for the 10 nearest chunks. FlashRank then rescored those 10 down to the 5 most relevant using a local cross-encoder, trading a bit of latency for much better precision than raw cosine similarity. 

async def retrieve_node(state: dict) -> dict:
    vector = await embedding_manager.embed(query)
    results = await qdrant_manager.search(vector, top_k=10)
    return {"retrieved_chunks": results, "thinking_steps": [step]}

async def rerank_node(state: dict) -> dict:
    results = await reranker.rerank(query, chunks, top_k=5)
    return {"reranked_chunks": results, "thinking_steps": [step]}

The reranker normalizes Qdrant’s ScoredPoint objects into plain dicts so the downstream nodes — and the frontend — only ever deal with a consistent shape: {text, source, chunk_index, score}.

generation with history

The generate node builds a single prompt from the reranked context, the previous conversation turn, and the current question. The context block is prefixed with source names and relevance scores so the model can cite claims.

the llm layer

Both the main generator and the guardrails run on Groq with openai/gpt-oss-20b; Portkey is the fallback gateway when no Groq key is set. A shared retry loop parses Groq’s “try again in XmYs” rate-limit message and backs off exponentially instead of failing.

Every node records a ThinkingStep (stage, detail, duration) which is stored separately from the message content. That is what powers the expandable “thinking” trace in the UI — the user sees the retrieval sources, rerank scores, and groundedness ratio without polluting the actual chat text.

ingestion: from raw scraped docs to clean chunks

The pipeline above assumes the vector store is already populated. The harder, often-ignored problem is what feeds it: raw scraped HTML from the Kubernetes docs site. A scraper pulls pages that include navigation, cookie banners, ad inserts, inline CSS/JS, and boilerplate that is repeated across hundreds of pages. If you chunk and embed that verbatim, your index fills with noise and duplicates — and retrieval quality collapses.

This section walks through a concrete two-stage cleaning pipeline we’re experimenting with before any text reaches the chunker or the embedding model.

sample inputs (raw scraped chunks)

chunk a (css/js noise): .nav-link { color: #333; margin: 0 10px; } function loadAnalytics() { window.dataLayer.push(arguments); }
chunk b (nav header & ad insert): Home > Products > RAG Systems. <div>Ad: Subscribe to our Newsletter!</div> Modern vector search uses HNSW indexes for approximate nearest neighbor retrieval.
chunk c (duplicate cookie notice): We use cookies to enhance your experience. By continuing to visit this site you agree to our use of cookies and Privacy Policy. (scraped across 50 different pages)
chunk d (low-quality short text): Read more... Share on Twitter.

stage 1: deterministic heuristics (regex & string metrics)

Stage 1 runs ultra-fast Python checks to eliminate non-text code artifacts and strip inline garbage. The key signal is the alphanumeric ratio — JS, CSS, and raw code are full of symbols ({ } ( ) # ;) so their ratio is low, while prose is mostly letters and numbers. 

import re

def stage_1_clean(text: str) -> dict:
    # 1. Strip inline HTML tags / noise patterns
    cleaned = re.sub(r'<div>.*?</div>', '', text, flags=re.IGNORECASE)
    cleaned = re.sub(r'<[^>]+>', '', cleaned).strip()

    # 2. Metric: Alphanumeric ratio (identifies JS, CSS, and raw code)
    alphanumeric_count = sum(c.isalnum() for c in cleaned)
    total_count = len(cleaned) or 1
    alpha_ratio = alphanumeric_count / total_count

    # 3. Decision
    if alpha_ratio < 0.65:  # Too many symbols like {}, (), #, ;
        return {"status": "REJECTED", "reason": "Low Alphanumeric Ratio (Code/CSS)", "text": None}

    return {"status": "PASSED", "reason": "Cleaned Inline Noise", "text": cleaned}

stage 2: deduplication & thresholding (micro-ml)

Stage 2 takes the chunks that passed Stage 1 and applies global deduplication via MinHash + LSH plus length/density thresholds. This is where the same cookie notice scraped from 50 pages collapses to a single fingerprint and gets dropped. 

from datasketch import MinHash, MinHashLSH

# Global store for tracking seen chunk fingerprints
lsh = MinHashLSH(threshold=0.8, num_perm=128)
seen_hashes = {}

def stage_2_filter(chunk_id: str, text: str) -> dict:
    words = text.split()

    # 1. Length Threshold (Drop tiny low-information chunks)
    if len(words) < 10:
        return {"status": "REJECTED", "reason": "Under minimum word count (< 10 words)"}

    # 2. Near-Duplicate Detection via MinHash
    m = MinHash(num_perm=128)
    for word in words:
        m.update(word.lower().encode('utf8'))

    duplicates = lsh.query(m)
    if duplicates:
        return {"status": "REJECTED", "reason": f"Duplicate of Chunk {duplicates[0]}"}

    # Store new unique hash
    lsh.insert(chunk_id, m)
    return {"status": "PASSED", "reason": "Unique and high quality"}

pipeline summary

Out of 4 raw, noisy scraped inputs: 75% of noise filtered instantly on CPU in less than 1 millisecond. One clean, high-value chunk (Chunk B) makes it to the embedding model and the Qdrant index.

From here the surviving chunks can go through an optional enhancement stage — for example a local vLLM serving a small model to reconstruct tables via OCR, repair broken HTML, and extract a summary or metadata (title, headers, reading time) that gets stored in the Qdrant payload alongside the chunk text. Only after that do the clean chunks flow into the existing chunk_text() splitter and the run_ingestion() upsert.

future steps

The system works end-to-end today, but there’s a long roadmap ahead:

streaming. The pipeline now streams via SSE: thinking steps arrive as the graph executes, tokens stream as the model generates, and a final done event carries the full answer. Perceived latency dropped dramatically — the first token appears long before the graph finishes.

evaluation pipeline. RAGAS is wired up in the test suite, scoring faithfulness, answer relevancy, context precision, and context recall against a 20-query dataset. Results persist to the EvalRun table with data and prompt versions.

document ingestion. Live — POST /api/ingest/upload accepts PDFs and images, OCRs them (RapidOCR + PyMuPDF), cleans and dedups (MinHash + LSH), then chunks, embeds, and ingests into Qdrant. Ingested files are tracked by checksum with list/delete/re-ingest endpoints.

memory. Conversations now persist long-term state via mem0 — the agent compacts every 5 turns into a searchable memory store and pulls relevant memories back into the prompt. A /api/chat/{id}/memory endpoint exposes what was stored per conversation.

real tool calls. The graph is currently a fixed six-node pipeline. Giving the model read-only Kubernetes tools (list namespaces, query pods, inspect cluster status) inside a tool-calling loop is the biggest open experiment — it turns the chatbot from a document-answerer into an operator.

intent-driven routing. The router classifies intent but the graph ignores it — every intent hits the same retrieval path. Routing by category (filter Qdrant by topic, tune top_k per intent) is cheap and high-impact.

semantic caching. The current cache matches exact queries. A semantic cache using embedding similarity would allow “how do I scale pods” and “how to autoscale deployments” to share a cache entry.

multi-modal support. Users should be able to upload architecture diagrams or YAML manifests and have the system analyze them visually or structurally.

cloud deployment. The Docker images and docker-compose.yml now deploy to Render — the backend (FastAPI, port 8000) and frontend (Next.js, port 3000) run as free-tier web services wired together by a Render Blueprint, with auto-deploys on push.
